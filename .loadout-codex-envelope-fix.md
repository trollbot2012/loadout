# Codex hooks.json envelope defect — fix report

## Defect

Codex refused to load ANY hooks at startup:
```
failed to parse hooks config C:\Users\Waxilliam\.codex\hooks.json: unknown field `PreToolUse`, expected `description` or `hooks`
```
Live file's root keys were `["hooks", "PreToolUse", "Stop"]`. Codex's schema accepts only
`description`/`hooks` at the root; the stray `PreToolUse`/`Stop` keys broke parsing for the
*entire* file, including every other tool's working hooks nested correctly under `hooks`.

## Root cause (scripts/apply.py, pre-fix line numbers)

- `codex_gate_hooks()` (45-52): returned `{"PreToolUse": [...], "Stop": [...]}` — an event map
  with no `hooks` wrapper — and wrote the handler key `command_windows` (snake_case) instead of
  Codex's canonical `commandWindows` (camelCase; `codex_hook_hash()` already tolerated both on
  read, so this only affected what got written).
- `register_codex_gate()` (99-104): its docstring said "events live at the top level" and it
  called `upsert_hooks(data, codex_gate_hooks())` — upserting straight onto the root `data` dict
  instead of `data["hooks"]`, planting the two invalid root keys.
- `trust_codex_gate()` (144-156): walked `data.get(json_key, [])` — the same wrong root-level
  assumption — so once entries move under `hooks`, its `gi`/`hi` indices would be computed
  against the wrong (empty) location.

## Fix

`scripts/apply.py`:
- `codex_gate_hooks()`: now writes `commandWindows` (canonical) instead of `command_windows`.
- New `_all_gate_entries(entries)`: true iff every handler in a list of groups is one of this
  repo's own gate entries (same `"gate.py"` substring match `upsert_hooks` already uses).
- New `_migrate_stray_root_events(data)`: for every root key other than `description`/`hooks`,
  if it holds *only* our own gate entries, move those entries under `hooks[key]` and delete the
  stray root key (this is the live-bug migration); if it holds *any* foreign entry, leave the
  whole key untouched and report its name back to the caller — third-party data is never moved
  or deleted on a guess.
- `register_codex_gate()`: runs the migration first, then upserts into `data.setdefault("hooks",
  {})` (the same `upsert_hooks` already used for Claude's `settings.local.json`, so the merge/
  idempotence/other-tool-preservation logic is shared, not duplicated). Appends a `WARNING:
  root-level <keys> left as-is (holds non-gate entries)` note to the returned action string when
  foreign stray keys were found.
- `trust_codex_gate()`: now reads `data.get("hooks", {})` before indexing by event name, so
  `gi`/`hi` are computed against the nested layout Codex actually parses.

## Migration behaviour for pre-existing bad root keys

- Root key holds only entries matching `"gate.py"` in their `command` → entries are appended
  into `hooks[<event>]`, the stray root key is deleted, then the normal upsert canonicalizes
  the entry (dedupes any stale copy, writes `commandWindows`). This is exactly what a machine
  hit by the live bug needs: rerunning `apply.py --host codex` self-heals the file.
- Root key holds a foreign (non-gate) entry, alone or mixed with a gate entry → the entire key
  is left byte-for-byte untouched and its name is reported in the action string. Nothing is ever
  destroyed to fix our own bug.
- Everything already correctly nested under `hooks` (other tools' entries, `description`) is
  preserved unchanged — verified by structural equality in tests, not just "still present".

## Tests

`tests/test_apply.py`:
- `assert_codex_schema_valid(data)` — the schema oracle: root keys ⊆ `{description, hooks}`,
  `hooks` is event→list-of-groups, each group has only `matcher`/`hooks`, each handler has
  `type == "command"`, non-empty `command`, and only known keys. Checks Codex-schema validity,
  not merely JSON validity.
- `test_codex_hooks_created_with_both_events_and_command_forms` — rewritten for the nested
  envelope (`data["hooks"]["PreToolUse"]` etc.), asserts the oracle.
- `test_codex_hooks_preserve_foreign_entries_and_replace_stale_gate` — rewritten with a realistic
  fixture (root `hooks` with a `devteam-codex.mjs hook PostToolUse` entry and a `commandWindows`
  entry already present); merge preserves every untouched entry via structural equality.
- `test_codex_migrates_stray_root_level_gate_keys_from_the_live_bug` (new) — regression for the
  live bug: valid root `hooks` PLUS invalid root `PreToolUse`/`Stop` holding only our own old
  gate entries → after apply, root-level keys gone, gate lives under `hooks`, nothing else lost,
  schema oracle passes, and a second run is byte-identical.
- `test_codex_foreign_root_level_key_is_preserved_and_reported` (new) — a root-level key holding
  a foreign entry is preserved verbatim and named in the returned action string.
- `test_codex_apply_is_idempotent` (new) — two runs, byte-identical file, exactly one gate entry
  per event.
- `test_trust_codex_gate_keys_match_nested_positions_not_root` (new) — a foreign group precedes
  ours under `hooks["PreToolUse"]`; asserts the trust key uses the nested index (`:1:0`), not a
  root-level index that wouldn't even exist under the fixed schema.

### What this commit actually changes

One real gap remained in requirement 3: the schema oracle existed and had the right docstring, but it
was **not applied after every codex write**. Three tests wrote a hooks file and never ran it through
the oracle. That is exactly the hole that let the original bug ship green, so it is closed:

- `test_codex_apply_is_idempotent` — oracle applied to the written file.
- `test_codex_host_writes_agents_md_and_user_hooks` — oracle applied to the file written through the
  full `apply()` entry point (previously the only codex write path with no schema assertion at all).
- `test_codex_foreign_root_level_key_is_preserved_and_reported` — this file's root is *deliberately*
  left invalid (the foreign root key is not ours to move), so the oracle is applied to the subtree we
  do own: `assert_codex_schema_valid({"hooks": data["hooks"]})`.

Proof the additions are load-bearing, not decorative — running the codex tests against the buggy
`main` copy of `scripts/apply.py`:


All 7 codex tests now fail against the buggy writer; all pass against the fixed one.
